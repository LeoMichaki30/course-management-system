# course-management-system

Online course management system developed with Node.js, TypeScript, Express.js and PostgreSQL through Supabase.

## Current scope

The first database stage includes the schema migration, development seed, SQL reports, and a server-only Supabase client. CRUD endpoints and authentication are not implemented. The existing root endpoint remains available independently of database configuration.

## Structure

```text
src/
  config/supabase.ts  # Server-only Supabase client
  models/            # Domain types for the next implementation stage
  repositories/      # Database queries for the next implementation stage
  controllers/       # Request handling for the next implementation stage
  routes/            # API endpoints for the next implementation stage
  app.ts

supabase/
  migrations/20261030000000_create_course_management_schema.sql
  seed.sql

```

## Database model

All entity IDs use `BIGINT GENERATED BY DEFAULT AS IDENTITY`. Foreign keys use `BIGINT`, and timestamps use `TIMESTAMPTZ`.

| Table | Relationships and constraints |
| --- | --- |
| `users` | Unique lowercase, trimmed `email`; `status` accepts `active` or `inactive`, defaulting to `active` |
| `courses` | Unique `code`; `user_id` identifies the creator |
| `modules` | `course_id` identifies the course; `user_id` identifies the module creator |
| `contents` | `module_id` identifies the module; `content` stores the content text |
| `user_content_views` | Required `user_id`, `content_id`, and `watched_at`; unique user/content pair |

Names, titles, codes, email addresses, and content text cannot be empty. Descriptions are optional. The module creator can differ from the course creator.

Foreign keys restrict deletion of users who created courses or modules, courses with modules, and modules with contents. Deleting a user or content removes the corresponding viewing records through `ON DELETE CASCADE` when no other restriction blocks the deletion.

`created_at` and `updated_at` default to the insertion time. Triggers refresh `updated_at` on every update. `watched_at` defaults to the insertion time, but a caller can supply the actual viewing time. The intended rule is to record the first viewing: a repeated user/content pair is rejected rather than replacing its timestamp. No automatic replay handler is implemented in this stage.

PostgreSQL `BIGINT` exceeds JavaScript's safe integer range. Future repositories must define a lossless ID serialization strategy before supporting IDs above `Number.MAX_SAFE_INTEGER`; the client configuration does not solve numeric decoding by itself.

## Supabase configuration

Use Node.js 22 or newer and a separate, empty Supabase development project. Do not apply the development seed to a production database or an existing dataset.

1. Install dependencies with `npm ci`.
2. Copy `.env.example` to `.env`.
3. Set `SUPABASE_URL` to the project's URL and `SUPABASE_SECRET_KEY` to its server-only secret key. A legacy `service_role` key can also be supplied through this variable. Never commit `.env` or expose this key to a browser.
4. In the development project's SQL Editor, execute `supabase/migrations/20261030000000_create_course_management_schema.sql` once.
5. Execute `supabase/seed.sql` once after the migration.
6. Run the queries in `sql/reports.sql` to inspect the sample results.

The SQL Editor steps are a minimal setup without a local Docker stack. The migration is versioned in the repository; SQL Editor execution does not automatically register it in Supabase CLI migration history. Before adopting CLI-managed deployments, reconcile that history instead of replaying the same migration. Neither the migration nor seed overwrites existing records or includes a database reset.

The migration expects Supabase's built-in `anon`, `authenticated`, and `service_role` roles. It enables Row Level Security on all five tables, grants no public policies, revokes table and sequence access from public client roles, and grants server operations to `service_role`. The server secret bypasses RLS and must remain private. This configures database access without implementing application authentication.

The client in `src/config/supabase.ts` reads environment variables and disables session persistence and refresh. It does not send a request merely by being imported and is not yet used by the API routes.

References: [Supabase client initialization](https://supabase.com/docs/reference/javascript/initializing), [server-only API keys](https://supabase.com/docs/guides/getting-started/api-keys), and [development seeds](https://supabase.com/docs/guides/local-development/seeding-your-database).

## Development seed

The seed creates five users, three courses, ten modules, fourteen contents, and seven viewing records.

| Course | Modules | Contents per module | Total contents |
| --- | --- | --- | --- |
| Course 1: Web Development | 5 | 1, 1, 1, 1, 1 | 5 |
| Course 2: Database Fundamentals | 3 | 2, 2, 1 | 5 |
| Course 3: Software Engineering | 2 | 2, 2 | 4 |

Course 1 receives five contents to satisfy the requirement that each of its five modules has at least one content.

Explicit IDs make the reports reproducible, including the query for content ID `2`. The seed advances each identity sequence after insertion so subsequent generated IDs do not collide. Rerunning the seed fails on existing unique values; it does not silently replace data.

## SQL reports and expected seed results

1. Users ranked by registered courses: Alice has two courses, Benjamin has one, and the other three users have zero. Ties are ordered by user ID.
2. Courses with the most contents: Courses 1 and 2 both have five; all ties are returned.
3. All courses with module and content counts: `(1, 5, 5)`, `(2, 3, 5)`, and `(3, 2, 4)`. Empty courses would be included with zero counts.
4. All contents with the course title: fourteen rows, ordered by content ID.
5. Users who watched content ID `2`: Alice, Benjamin, and Chloe, with their `watched_at` timestamps.

## Verification

```sh
npm run typecheck
npm run dev
```

The server listens on `http://localhost:3001`. The root endpoint tests Express availability only; it does not test the database.

To check a real Supabase connection after configuring a development project, run this read-only query from the repository root:

```sh
npx tsx -e 'import { supabase } from "./src/config/supabase"; supabase.from("courses").select("id, code, title").order("id").then(({ data, error }) => { if (error) { console.error("Supabase query failed:", error.code); process.exitCode = 1; } else { console.log(data); } });'
```

A successful TypeScript check or client initialization does not validate migrations or a Supabase connection. Validate those by actually applying the SQL to a development database and executing the reports and connection query. No commit, push, reset, or production deployment is part of this stage.
